# Cache keys

What every TanStack Query cache in `apps/web` holds, and **which mutations must reach it**.

Stale-data bugs happen when a mutation changes data and fails to invalidate a query that
displays it. That failure is silent by construction, so this exists to make the cascade
auditable rather than guessed.

> **Query keys are an exact vocabulary.** `invalidateQueries({ queryKey: K })` refreshes a
> query only when `K` is a **prefix** of that query's key, compared element by element. A key
> spelled differently at one call site matches nothing, refreshes nothing and reports nothing.

The convention is `../basket-bot`'s, which arrived at it after cache refreshing became the
single most churned area of that codebase. Its version is
`apps/mobile/src/db/queryKeys.ts` + `apps/mobile/docs/CACHE_KEYS.md`; this is the same idea at
this app's size.

## 0. Required: build every key with the factory

**Never hand-write a `queryKey` array.** Every key is declared once in
[`apps/web/src/lib/api/queryKeys.ts`](../apps/web/src/lib/api/queryKeys.ts) and must be built
by calling a function on the exported `queryKeys` object. A mistyped factory call is a compile
error; a mistyped array is a bug that shows up days later as data that is merely out of date.

```ts
useQuery({ queryKey: queryKeys.media.page(filter, page), queryFn: … })
queryClient.invalidateQueries({ queryKey: queryKeys.library.roots() })
```

This is enforced. [`queryKeys.test.ts`](../apps/web/src/lib/api/queryKeys.test.ts) walks every
source file under `apps/web/src` and fails on any `queryKey: [`, naming the file. It is a lint
rather than a type check because the compiler cannot object to an array literal.

### The viewer's walk

The viewer steps through the set it was opened from (`useViewerSequence`). It used to hold the
grid's own `media.page` tiles, and stepping remounts it (§14b), so every step more than 30
seconds after the last refetched the whole page with every tile hydrated — two hundred of them
from the showcase, on a disk that charges per page (§20). Working through "Untagged
performers" refetched it after nearly every tag.

It now walks `media.idsPage` and draws only what is on screen: the item and the next one from
`media.detail`, the up-next strip from `media.lookup`. The decision on refreshing:

- **The ids page is asked again on every arrival** (`staleTime: 0`), because it is cheap now
  and the offsets depend on it. Tagging the item in front of you takes it out of a filter like
  "Untagged", which moves everything after it one place earlier; a page held for many steps
  would ask for the next page at an offset past the items that slid onto this one, and the
  walk would skip them.
- **What a step shows is held from its arrival.** The current page is held from the first
  answer that contains the item (usually the cache, so arriving is instant), the adjacent page
  from its first fresh answer. Tagging or rating mid-item refetches nothing it is standing on
  — the item tag mutation does not reach `media.all()` at all, and a rating's refetch is
  ignored by the hold — so the next button never moves under somebody's click.
- **An item that has left the set does not trap the walk.** The page held for the previous
  step is remembered, and an item no fresh answer contains — the one just tagged out of
  "Untagged", stepped back onto — is placed by it. Adjacent pages are de-duplicated against the
  current one so an overlap cannot walk in a circle.

**Behind these keys, the server keeps an order** (§20 "A shuffle is sorted once",
`keptOrders.ts`). A shuffle, and an untagged list while it is being walked, is sorted once per
viewer, filter and seed and kept for five minutes; `media.page`, `media.idsPage` and
`media.count` for it are all slices of that one order. Nothing here changes on the client, and
no client key has to reach it: a slice is re-checked against the filter when it is served, so an
item that left the set — tagged, rated, hidden, trashed — is gone from the next refetch as
before, and its slot stays empty rather than the rest moving up (which is what the walk wants).
The count drops it once a slice has found it gone. An item that **joins** a set by an edit
(untagged again, re-rated into it, restored from the bin by the worker) appears when the order
expires; a new file is noticed at once (the newest rowid is checked on every use), and the
server's `clearLibraryCaches` empties every kept order on trash, hide and any library change.
A "find untagged" list is also run by date added whatever its address says (`withSortOverride`),
so the shuffle in such an address never reaches the database; the client keys still carry it,
which is harmless — one filter, one key, as before.

**Rule of thumb:** a mutation must invalidate the key of every cache in §1 whose _Holds_
column includes anything the mutation can change — not only the obvious one.

## 3. Keeping this current

Touching caching means touching this file in the same change:

1. **New query** → add a builder to the factory **and** a row to §1.
2. **New or changed mutation** → add or update its row in §2.
3. **A cascade shared by several call sites** → give it a named function beside the mutations
   it serves, as `invalidateLibraries` does, so the set is stated once.

Not built here: `../basket-bot` drives every mutation hook in a test and asserts the exact set
of keys it invalidates, with a coverage guard that fails when a new hook has no documented
cascade. That needs a hook harness this app does not have, and this app has a fraction of the
mutations. §2 is prose until that changes; §0 is enforced today, and §0 is what the two bugs
this file was written for would have needed.
